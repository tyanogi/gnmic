# Track Specification: Implement Suggestion Engine & Cache (Track 2)

## 1. Overview
gNMIcのプロンプトモードにおいて、YANGスキーマから抽出されたリスト情報を基に、その具体的な候補値（例：インターフェース名、OSPFエリアIDなど）をターゲットデバイスから非同期に事前取得（Prefetch）し、キャッシュする機能を実装します。これにより、ユーザーがパスを入力する際に、実機から取得した最新の候補値を即座に補完候補として提示できるようになります。

## 2. Functional Requirements
- **キャッシュ機構 (`suggestion_cache.go`)**:
    - `sync.Map` を使用したスレッドセーフな Key-Value ストア。
    - **Key**: リストのスキーマパス（String）。
    - **Value**: 取得された候補値のリスト（[]string）。
    - **ライフサイクル**: プロンプトモードのセッション中のみ保持（終了時に破棄）。

- **事前取得エンジン (`suggestion_engine.go`)**:
    - **トリガー**: プロンプトモード起動時に、Track 1で抽出されたすべてのリスト情報に対して実行を開始します。
    - **非同期実行**: メインのCLI入力を妨げないよう、各リストの取得は個別の Goroutine で実行されます。
    - **取得方法**: 各リストの `StatePath` に対して個別の gNMI Get リクエストを送信します。可能な限り既存のgRPCセッション（クライアント）を再利用し、接続オーバーヘッドを最小化します。
    - **レスポンス解析**: gNMI GetResponse から値を抽出し、重複を除去してキャッシュに保存します。

- **エラーハンドリング**:
    - デバイスへの接続エラー、タイムアウト、権限エラーなどが発生した場合は、そのリストの取得を静かに中止し、ログを出力します。CLI全体をクラッシュさせたり、ユーザー入力をブロックしたりしてはいけません。

## 3. Non-Functional Requirements
- **パフォーマンス**: バックグラウンドでのリクエストがターゲットデバイスやネットワークに過度な負荷をかけないよう、必要に応じて並行数の制限（Workers）を検討します（初期実装ではシンプルさを優先）。
- **一貫性**: 既存の `pkg/app` 内の設計パターンや命名規則に従います。

## 4. Acceptance Criteria
- [ ] `pkg/app/suggestion_cache.go` と `pkg/app/suggestion_engine.go` が作成されている。
- [ ] プロンプトモード起動時にバックグラウンドでリクエストが送信されていることを（ログ等で）確認できる。
- [ ] 取得された値が `suggestion_cache` に正しく保存されている。
- [ ] ネットワークエラー時もプロンプトモードの操作が継続できる。
- [ ] ユニットテストですべての正常系・異常系がカバーされている。

## 5. Out of Scope
- キャッシュのディスクへの永続化。
- gNMI Subscribe を利用したリアルタイムなキャッシュ更新。
- 複数のパスを1つのGetリクエストにまとめる最適化（gRPCセッションの再利用は行うが、リクエスト自体は個別）。
